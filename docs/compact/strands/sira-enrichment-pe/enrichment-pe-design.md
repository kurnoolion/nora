# sira-enrichment-pe — design

Prompt engineering + throughput for SIRA doc-enrichment. Settled through
dialogue 2026-07-24; sizing numbers from `sandbox/scan_enrichment_stats.py`
run on the full deployed corpus (23,252 enriched requirements).

Measured baseline (current single-req enrichment):
- phrases/req: mean 9, p50 10, p95 10, max 20
- response tokens/req (strict-JSON form): mean 65, p50 65, p95 86, max 127

## 1. Per-MNO prompts

Today: one prompt, generated by the Cline corpus-scan skill when only the
first MNO was ingested; every cell uses it.

Design:
- One prompt file per MNO at `customizations/prompts/
  doc_requirement_<MNO>_<version>.txt`. **Committed — but internal
  remote only** (decision 2026-07-24, superseding the earlier
  "runtime artifact, never committed" posture): per-MNO files carry
  real MNO names + harvested vocab, so they follow the D-062
  mapping-snapshot rules — committed/pushed only from the work PC to
  the company-internal remote, kept off the public mirror by the
  work-PC pre-push hook. Both docker images COPY customizations/ at
  build, so containers resolve them at /app/customizations/prompts.
- Resolution at pipeline run, per cell: exact per-MNO file, else the
  legacy single prompt with a loud log line. The chosen prompt snapshots
  into the run dir (existing `prompt.txt` provenance mechanics — now
  per-cell-correct by construction).
- The Cline prompt-generation skill becomes MNO-parameterized: takes an
  MNO, scans only that MNO's corpus, writes the per-MNO overview to the
  fixed filename. Re-run per MNO on ingestion of a new MNO or material
  corpus change — a standard step, not an ad-hoc session.

## 2. Prompt composition (per batch)

Ordered sections:
1. **Corpus overview** — the per-MNO AI-scanned section (as today).
2. **Taxonomy block** — prologue: "the following is the feature taxonomy
   — features, key concepts, and keywords — of the plan these
   requirements belong to", then the WHOLE per-plan taxonomy file
   (≤5k chars ≈ 1.4k tokens). Source: NORA taxonomy stage output —
   `<env_dir>/out/taxonomy/<plan_id>_features.json` (per-plan
   DocumentFeatures files written alongside the consolidated global
   taxonomy.json; no curation layer exists — files are used as
   generated). Wiring: one configurable taxonomy-dir knob; the
   plan→file mapping is the existing `<plan_id>_features.json`
   convention. Missing taxonomy → omit the block, log a warning,
   enrich anyway (fail-soft).
3. **Task instructions** — enrichment task + strict-JSON output spec +
   phrase cap (≤10 per requirement; measured p50 is already 10) — the
   cap is what makes the response-size bound enforceable.
4. **Packed requirements** — each delimited with its req_id header;
   requirement text verbatim, never fragmented.

**Template contract** (generated per MNO by the derive-sira-prompts
skill; filled per batch by the composer): the per-MNO doc prompt file
contains the overview/subdomain/instruction sections as static text
plus exactly these placeholders — `{taxonomy_block}` (plan taxonomy,
empty string when missing), `{requirements}` (packed reqs, each under
a `### req_id: <id>` header), `{max_n}` (max words/phrase). The old
single-req `{doc_text}` is gone. Output spec inside the template:
req_id-keyed strict JSON, every packed req_id present, ≤10 phrases
each. Prompt files: `customizations/prompts/
doc_requirement_<MNO>_<ver>.txt` (work-PC generated; committed to the
internal remote only — see section 1).

## 3. Batch creator

- Group by **(MNO, release, plan)** — one taxonomy block per prompt.
- Resume-aware: composed from the not-yet-done req_ids only (per-req
  trace remains the state; batches are transport, not state).
- Token estimation: conservative chars-per-token heuristic (default 3.5,
  configurable) — no tokenizer dependency.
- **Dual budget** (the scan's key finding — the response can overflow
  before the prompt does):
  - Prompt side: measured header size (overview + taxonomy + instructions,
    composed first and counted — not estimated) + Σ req text ≤ cap
    (default 50k tokens of the 64k context).
  - Response side: reqs_in_batch × resp_est ≤ reserve (context − cap =
    14k). resp_est default 90 tokens (measured p95 86). At defaults:
    ≤ ~155 reqs/batch regardless of how small the texts are.
  - Batch closes when EITHER budget would be exceeded by the next req.
- Never fragment a requirement. A single req that alone exceeds the
  prompt cap ships as a solo oversized batch with a warning (skipping
  would silently lose enrichment).
- Small-plan coalescing: **rejected for v1** (user decision) — strict
  one-plan-per-batch; at least one batch per plan is acceptable. Every
  batch logs its size (plan, reqs packed, prompt tokens est, projected
  response tokens, which budget closed it) so the coalescing question
  can be revisited from data if tiny batches turn out to dominate.

## 4. Response contract

- Strict JSON: `{"<req_id>": ["phrase", ...], ...}`.
- Per-req validation: phrases must be a list of strings; req_ids not in
  the batch are ignored + logged; req_ids missing from the response are
  re-queued into fresh batches with bounded retries (default 2), then
  traced as failed — the cell serves vanilla BM25 for those reqs
  (existing fail-soft posture).
- Trace rows stay per-req (id, phrases, batch_id) — batch_id is
  observability metadata, not state.

## 5. Observability

Run summary gains: batch count, mean fill % (both budgets), retry
counts, oversized-solo count, response-truncation detections (JSON
parse failure on a length-capped response is the signature). Per-req
trace unchanged otherwise; resume semantics identical to today.

## 6. NORA taxonomy-prompt cross-pollination

The taxonomy is now enrichment INPUT, so its quality compounds. No
curation layer exists (confirmed) → regenerating taxonomies is safe and
cheap.

Mechanism (NORA's taxonomy prompt is CODE, not a file —
`core/src/taxonomy/extractor.py` SYSTEM_PROMPT +
EXTRACTION_PROMPT_TEMPLATE, fed only TOC headings + plan metadata):
- The derive-sira-prompts skill additionally writes the per-MNO
  overview as a standalone artifact
  (`customizations/prompts/corpus_overview_<MNO>_<version>.txt`) —
  derived once per MNO, consumed by BOTH the SIRA doc prompt and
  NORA's taxonomy extractor.
- `FeatureExtractor` gains an optional corpus-overview input (config
  knob → per-MNO overview file resolved by the doc's MNO); when
  present it is inserted as a "Corpus context" section in the
  extraction prompt; absent → exactly today's behavior (fail-soft).
  Core `taxonomy` module change + MODULE.md update; taxonomy stage
  cache note: the corpus fingerprint does NOT include the overview
  file, so regeneration after adding an overview needs `--force` (or
  the fingerprint gains the overview hash — decide at implementation).
- Then regenerate taxonomies per MNO and re-run enrichment against
  the improved files.

**Staging decision: COMBINED** (user decision, 2026-07-24). Both levers
(enrichment prompt + regenerated taxonomies) ship in ONE re-enrichment;
the result is the new baseline. Rationale: no expert correction records
exist yet, so a staged rollout would be measured against nothing firm —
attribution only becomes meaningful once the evaluation loop (separate
strand) establishes corrections. From then on: one lever per iteration,
scorecard attributes each change.

## Implementation slices

1. Sizing scanner — DONE (`sandbox/scan_enrichment_stats.py`, f5ff935).
2. Cline skill MNO-parameterization + batched doc-prompt contract —
   skill + playbook DONE (derive-sira-prompts SKILL.md step 7 carries
   the contract); per-MNO prompt regeneration itself runs on the work
   PC (once per MNO) after slice 4 lands, so the generated templates
   are consumed by real composer code, not ahead of it.
3. Taxonomy wiring + prompt composer (sections 1–2) — DONE
   (`sandbox/enrich_batching.py`: taxonomy block loader, per-MNO prompt
   resolver, composer).
4. Batch creator + adapter integration + response parsing/retry
   (sections 3–4) + observability (section 5) — DONE: dual-budget
   packer + strict parser + run_batched orchestration in
   `sandbox/enrich_batching.py` (19 unit tests, no clone needed);
   `sandbox/sira_patches/batched-enrich.patch` wires the adapter
   (auto-activates on batched-shape template; legacy path untouched;
   per-req trace rows + `batches.jsonl` in the run dir; applies
   cleanly after per-stage-routing.patch — verified); knobs in
   `docker/env.sira-batch.example` (NORA_SIRA_DOC_PROMPT_DIR,
   NORA_SIRA_TAXONOMY_DIR, NORA_SIRA_BATCH_*).
5. Taxonomy-prompt update + regeneration (section 6, staging decision
   applied), then full re-enrichment across cells — NORA half DONE:
   `FeatureExtractor(llm, overview_dir=)` + `resolve_corpus_overview`
   (highest-version glob, fail-soft TAX-W003); `{corpus_context}`
   section in the extraction prompt (byte-identical when absent);
   `run_taxonomy` reads `NORA_TAXONOMY_OVERVIEW_DIR` and hashes the
   overview files into the corpus fingerprint (cache decision:
   fingerprint gains overview hash — no `--force` needed);
   `taxonomy_cli --overview-dir` parity; taxonomy + pipeline MODULE.md
   updated; 6 new tests (suite 1541 green). Remaining: the work-PC
   regeneration + combined re-enrichment run (user-driven).
