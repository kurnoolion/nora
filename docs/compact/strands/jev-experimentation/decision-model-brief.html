Decision models for NORA query classification

What a “System One” decision model is, why the hosted product is unusable for us, which open model we can actually run, and what it would realistically buy NORA.

Status design draft v0.9 Date 13 Oct 2026 Target query classification Code written none

The short version

A decision model answers a typed question — a choice, a yes/no, or a score — in one forward pass, generating no text. That is the whole trick, and it is why the category is fast.

TypeSafe’s Jev is the product that named the category. We cannot use it: closed weights, hosted only, no on-premise option, and our build and serve environment permits no external calls. So the question becomes whether an open decision model, running in-corp, should take over NORA’s query classification.

It can. Kev-4B runs today on the on-prem GPU host we already have, Apache-2.0 throughout, no new serving infrastructure, and it works zero-shot — the ten categories are passed in at query time, not trained in. No telecom-specific training is required, and none is proposed.

Concept

What a decision model actually is

Every transformer has two parts: a stack that turns text into hidden states, and a thin final layer — the head — that turns the last hidden state into output.

A normal LLM has a language-model head: hidden state to a probability over the whole vocabulary. Pick a token, append it, run again. Producing N tokens costs N serial passes, so latency scales with how much it writes.

A decision head maps that same hidden state straight onto your option set — K choices, or one yes/no probability, or a score level. One pass, no tokens, and latency independent of K: ten options cost what two do.

The vocabulary is interchangeable: decision model, head-bearing model, System One model all name the same thing. “Classification model” is narrower — classification is one of three output shapes, alongside score and boolean.

None of this is new. Bolting a head onto a transformer has been standard since BERT in 2018, and NORA already ships one: CrossEncoderReranker runs ms-marco-MiniLM-L6-v2, a transformer with a scoring head. What is new is training specifically for calibrated probabilities, and a typed API that evaluates many questions against one shared input in parallel.

Constraint

Why it cannot be Jev

TypeSafe released Jev on 15 September 2026. It returns only bools, scores and choices with calibrated probabilities; 70–500 ms end-to-end; $0.042 per million input tokens with output free; questions in one request evaluated in parallel against a shared state.

It is also closed weights, hosted only — no VPC, no on-premise, no self-hosting. US West Coast with no region choice. Retention is “as long as reasonably necessary”, with zero-retention negotiable through enterprise sales. SOC 2 Type II is third-party reported but not confirmed in TypeSafe’s own documents; no ISO 27001.

Our corpus is proprietary MNO requirement content, and our build and serve environment permits no external API calls at all. There is no configuration in which hosted Jev runs against this corpus. No vendor contract is needed or wanted — “Jev” from here means Jev-class, not the product.

Use case

What NORA does today, and where this would sit

Every NORA query starts at the query analyzer, which assigns one of ten QueryType values and one of three DocTypeScope values. Today that is done entirely by ordered keyword rules — MockQueryAnalyzer. An LLM-based analyzer exists in the codebase but is never wired into any live path.

The rules are not naive. Precedence is deliberate: FACT is tested before definitional patterns so “what is the maximum X” isn’t mis-routed; STANDARDS_COMPARISON precedes RELEASE_DIFF because “differ” overlaps “diff”. They work because engineers ask in formulaic shapes. They are brittle to any phrasing nobody anticipated, and they do not scale as classes and phrasings multiply.

This one label configures the entire pipeline

intent.query_type is read at thirteen sites in the query pipeline. It selects:

top_khow many chunks retrieved
bm25_weightBM25 vs vector balance
rerankreranking on or off
rewritewhether expansion runs
max_distancerelevance cutoff
groupinggroup results or not
system promptwhich synthesis prompt
cell scopewhich corpora are searched

So classification is the highest-leverage single decision in the pipeline — everything downstream is parameterised by it. It must also stay before query enrichment, because enrichment only runs if the classified type enables it.

Consequence for measurement

Overall accuracy is the wrong metric. FACT and SUMMARIZE select opposite configurations — tight top_k with a strict 0.4 cutoff and reranking on, versus wide top_k with a 0.7 cutoff and grouping off. A classifier at 95% that confuses those two can be worse in practice than one at 85% that confuses near-identical types. We will report a confusion matrix weighted by how far apart the downstream settings are.

What we can actually run

Kev is the pick. Canonical upstream is jaredpalmer/kev (9.1k stars; the several identically-named repos are forks). Each checkpoint is a rank-16 LoRA adapter plus a small bilinear pointer head on an Apache-2.0 Qwen base — and Apache-2.0 covers the adapter and head too, not just the base. It ships its own server exposing /v1/systemone, so no vLLM work is needed for the first iteration.

One flag matters: the card notes 4B at fp32 needs ~16 GB, which would consume the whole card. KEV_DTYPE=bf16 halves that.

A route back to the bigger models exists and is worth recording. AWQ quantisation via llm-compressor keeps the decision head at full precision while compressing only the backbone — the published JEV-27B-VL-AWQ does exactly that. Applied to JEV-9B (18 GB at bf16, ~5 GB at 4-bit) it should fit our card, and JEV-9B’s numbers are the strongest available: KL ≈ 0.019 against hosted Jev and 90% of its accuracy at 16 options. Nobody has published a JEV-9B-AWQ, so we would be first — which is why it is a later entry, not the opener.

Requirement — the trap to avoid

These models keep the backbone frozen and add a small detachable decision block; for JEV-9B it is 40.2M parameters, about 0.5% of the backbone. Because it is detachable, it ships as separate files — and standard GGUF conversion drops it. The popular GGUF builds are plain Qwen or Gemma wearing a decision-model name. They load, they answer, and nothing errors.

Since NORA serves local models through Ollama, which is GGUF-based, the most natural integration path is the broken one. Verification before any number is recorded: the file list must contain head.safetensors, an adapter folder and calibration.json. A hollow build contains only .gguf files.

A fifth option deserves naming because published evidence favours it: a small purpose-trained classifier. A 200M DeBERTa scored 89.01% at 54 ms against hosted Jev’s 86.35% at 348 ms on prompt-injection detection. The usual guidance is “if you have labels, start with a small classifier.”

That tension resolves rather than competes here. Kev is LoRA-trainable, so a Kev fine-tuned on our labelled queries is that small purpose-trained classifier — with calibrated typed outputs and a standard interface on top. The two arms merge.

Risk

What will go wrong, stated in advance

Kev-4B’s own model card reports in-distribution accuracy 0.854 but out-of-domain accuracy 0.790, with ECE 0.096 described explicitly as uncalibrated out of domain. Its limitations section says that “product-shaped questions with no training analogue are not guaranteed.”

It is worth being precise about why, because the obvious reading is wrong. The gap is not that it lacks telecom knowledge — our classifier reads plain English questions, never spec text, so telecom vocabulary is irrelevant to it. The gap is that it has never seen our label set. It was trained to sort banking intents, news topics and film sentiment. It has never been asked to sort a question into NORA’s ten categories, and RELEASE_DIFF or TRACEABILITY are our taxonomy, not English concepts.

Some of those boundaries are not determinable from English at all — they are NORA conventions. Our own code documents the clearest case: “explain the X authentication requirements” routes to SUMMARIZE rather than SINGLE_DOC even though it names a plan, because the user wants the topic surveyed rather than one requirement looked up. No amount of language understanding produces that answer; it is a decision we made.

So: no telecom fine-tuning. Possibly a small task fine-tune.

Domain training is explicitly rejected. Continued pre-training on spec prose would teach the model the language of documents, a different distribution from the language of questions about documents — the wrong target, and it would also bake proprietary content into weights.

What may help instead is ordinary task fine-tuning: a few hundred labelled example questions teaching it where our category boundaries sit. And the convenient part is that we need that labelled set for evaluation anyway — one artefact, two uses. Nothing extra to collect.

It is also not a prerequisite. Kev classifies zero-shot, so the sequence is: run it against the labelled set, read the confusion matrix, and fine-tune only if the errors cluster on category boundaries. If zero-shot is good enough, we stop there.

One cautionary precedent, with its limits stated. The A11 run put a generic cross-encoder reranker into the pipeline and it came back net-zero at 86.4% / 62.3%, diagnosed as out-of-distribution on telecom text. That is a real warning about generic models on NORA tasks — but it is not a direct prediction here, because that reranker scored query-against-chunk pairs over spec prose, and our classifier never touches spec prose. Treat Kev’s own 0.790 as the number to expect, not A11’s.

Two further honest costs. Latency rises from effectively zero to perhaps 100–200 ms — small against a pipeline that already makes an LLM expansion call and an LLM synthesis call, but real, and it will be measured rather than assumed. And we trade away inspectability: when a rule misfires you read the rule and fix it; when a model misfires you can only measure it. The evaluation set is not overhead bolted onto the experiment — it is the replacement for debugging by inspection.

There is also no classification evaluation today. The A-series runs measure the pipeline end to end, not the classifier. Labelled examples exist only in unit tests, skewed by history, with zero coverage for three of the ten classes. Building that set is the first real task.

Scope

What this does and does not buy

One correction worth stating plainly, because it changes the business case: this seam does not currently use an LLM. A decision model here replaces keyword rules, so iteration one saves zero LLM tokens. It buys better classification, scalability, and the expertise — not cost reduction.

The decision points that do spend LLM calls are reranking, SIRA chunk selection, query expansion and the golden-eval judge. All of those read chunk bodies, which is why they are not first. If cost reduction rather than capability is the goal, the ordering should be reconsidered.

Roadmap

Where this goes in NORA

Query classification is deliberately the safest, cheapest place to learn the category: it reads only the user’s question, never corpus content; it has an existing baseline to beat; and the integration point is a single factory function. Once the pattern is proven, six other decisions in NORA have the same shape.

Candidate decision points beyond iteration one

The expansion toggle is the standout: it is the one place where the token-cost motivation, the latency concern and a known recorded pain all point the same direction. It is also the natural home for domain-adaptive training later, since those decisions read spec text — where teaching the model telecom language would genuinely help, unlike query classification, which reads plain English questions.

Decisions needed

What we need from you

  1. If zero-shot falls short, is a task fine-tune in scope for this strand? Not telecom training — just a few hundred labelled questions teaching it where our ten category boundaries sit, using the set we need for evaluation regardless. Roughly a day of work. We would only reach for it if the confusion matrix shows the errors clustering on boundaries.
  2. Why is classification rule-based today? There is no decision record. If an LLM was tried and rejected on latency, this revival is directly well-motivated. If it was never wired for plumbing reasons, then no model has ever been measured at this seam and our baseline would be the first such comparison ever run. Either answer is useful.
  3. Module placement — a new core/src/decision/ package, or extend core/src/llm/?
  4. What result would justify making this the default? Worth agreeing now, so it isn’t relitigated later against a moving bar.
  5. Infrastructure detail — the production image name for a later default-on rebuild, and the exact specification of the synthesis backup host, which would reopen the larger models.
