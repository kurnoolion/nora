Strand · llm-model-choice

The 15-Second Answer

Why RAG synthesis is slow, and the two controls that let anyone find out: which model answers, and whether it should think.

Status proposal for review Date 2026-09-01 Branch llm-model-choice Modules llm · web · env · query

Two problems, currently fused

Synthesis takes roughly 15 seconds. We traced it to the Qwen3 30B model running in reasoning mode on our vLLM endpoint — it generates thinking tokens we then throw away. That produced a feature idea: let people choose the model and reasoning level per question.

Those are two different things and should be decided separately.

Problem A · latency

Thinking tokens we never show

The model reasons, we strip the reasoning, the user waits for it anyway. Nothing in the product needs this.

Addressed per request, at the Ask knob — not at the server.
Problem B · capability

No way to compare setups

One provider is resolved process-wide. Trying a different model or reasoning level means editing config and restarting.

This plan. Worth doing on its own merits.
Decided: a server-wide off switch exists and would remove the latency with zero code — and we are deliberately not using it. The serving default stays reasoning-on; the knob belongs in the Ask lane, per request, so we can try both rather than commit the whole serving stack to one mode.

The consequence to accept knowingly: with the server default unchanged, reasoning-on stays the default experience, so ~15 seconds remains the default latency until a user turns it down. That makes what the Ask control defaults to the real latency decision — see the open questions.

What the code already does

All verified in the repository, not assumed:

  • The provider seam has no reasoning parameter — and changing it is a coordinated break across taxonomy, query and eval. We do not touch it.core/src/llm/base.py · complete(prompt, system, temperature, max_tokens)
  • Configuration resolves one provider, not a roster. Config page → env var → config file → environment JSON → default, as flat hand-curated fields.core/src/web/config_schema.py · D-044 / D-053
  • The Ask page has two synthesis lanes, with opposite caching behaviour — and this is the plumbing cost of the whole feature. The pipeline lane builds its provider and synthesizer once and caches them until the process restarts, so a per-question knob cannot reach it without a change there. The select-synth lane builds one per call and is free.core/src/web/routes/playground.py — pipeline lane via query.py:513 (cached on app.state) · select-synth at playground.py:683 (per call)
  • Mutating the cached provider per request is not an option. Queries run on background threads, so two concurrent asks at different levels would clobber each other and record provenance that does not match the answer.asyncio.create_task → asyncio.to_thread
  • Our existing reasoning code strips output; it does not disable thinking. Chain-of-thought is discarded after generation, so the latency is still paid in full. This is why earlier work here did not make answers faster.core/src/llm/openai_provider.py · _strip_reasoning, NORA_LLM_REASONING_SENTINEL
  • We can already record what produced an answer. The model column and a config JSON column both exist and are already accepted by the write path — no migration.core/src/web/feedback_db.py · test_feedback.llm_model, lane_config

The reasoning control on vLLM

From the vLLM stable documentation, Reasoning Outputs. Three forms, two of them per-request:

// per request — Qwen3, broadly supported
"chat_template_kwargs": { "enable_thinking": false }

// per request — OpenAI-standard; vLLM maps it to enable_thinking itself
"reasoning_effort": "none" | "low" | "medium" | "high"

// server default — available, deliberately NOT used
--reasoning-parser <parser> --default-chat-template-kwargs '{"enable_thinking": false}'

reasoning_effort is the standard field and vLLM does the mapping to enable_thinking server-side. That kills the capability registry I first sketched: we need one passthrough field, not a per-model support table.

Known risk: reasoning_effort support is vLLM-version dependent; chat_template_kwargs is the older, safer path. Step 1 below is a five-minute probe against the deployed server. Same interface either way — only the request body key changes.

The work, in phases

Phase 1

Ask page · named providers · Fast / Think · both lanes

  1. Probe the deployed vLLM for reasoning_effort versus chat_template_kwargs. Verify one form returns 200 with visibly lower latency and an empty reasoning field.
  2. Give the openai-compatible provider an optional reasoning argument at construction, adding the corresponding key to the request body. The shared provider interface is untouched. Verify a unit test asserts the body carries the field when set — and is byte-identical to today when it is not.
  3. Let the Ask request override the resolved reasoning level; an absent value keeps today's behaviour exactly. The model stays whatever configuration resolves. Verify an Ask with no override resolves the same provider as before.
  4. Decouple the LLM from the cached pipeline: the query call accepts a synthesizer for that one question, so a request carrying a reasoning level gets its own provider while the expensive pipeline — graph, embedder, vector store, keyword index — stays cached. Provider construction costs no network call. Verify cold-start cost is unchanged on a second query, and a query with no override still uses the cached provider.
  5. Thread the level from the form to every synthesis path on the page. The background-job plumbing this step originally called for turned out to be unnecessary: the Ask page runs its query directly, so the jobs table is untouched. Verify all six synthesis paths — both lanes, the streaming variant, the two legacy paths and the disambiguation follow-up — pass the level through.
  6. Two controls on the Ask page: a provider picker showing named endpoints ("130B — DGX", "14B — internal"), and a Fast / Think toggle. Fast skips thinking; Think sends no reasoning field at all, so the deployment's own behaviour applies — we never assert an effort level on its behalf. Names say what the infrastructure is, because "primary" means nothing to the person asking. Verify the same question is measurably faster on Fast, and each provider logs its own model.
  7. Reasoning support is declared per provider, never detected — no endpoint advertises the capability, and a probe only catches outright rejection, since a server can accept the field and silently ignore it. Declaring it means a provider with no knob shows "Not supported" instead of offering a choice that would do nothing. Note this is about the endpoint honouring the knob, not about whether the model reasons: a thinking model with no exposed control is still "no". Verify the control reads "Not supported" on an endpoint declaring no control, and no reasoning field is sent.
  8. Record the provider, the mode and the model that answered on the answer row, reusing columns that already exist — so an answer is attributable to a (provider, mode, model) triple. Verify two asks at different settings produce two rows that differ.
Configuration. An optional providers list in config/llm.json, with config/llm.json.example as the copy-from reference. Keys are referenced by env-var name, never written in a committed file. Omit the list — the normal case — and nothing changes: the controls are not rendered and the single-provider chain runs exactly as before.

Out of Phase 1: Ollama reasoning, evaluation, enrichment, taxonomy.
Phase 1.5

Evaluation — next, but a different shape

Evaluation is the immediate second lane, and it is not the Ask control moved sideways. Golden eval depends on snapshot freeze and a fixed serving environment; a per-question override leaking into a run would silently break comparability between cells.

The right shape: model and reasoning are properties of a campaign cell — fixed for the run, recorded in the manifest, an arm to flip rather than a control to twiddle. Designed when we get there. Phase 1's only obligation is to not expose an override that evaluation can inherit by accident.

Phase 2

The provider roster — needs a decision

The horizontal goal — LLM providers as a component anyone configures — means named provider entries in settings, with Ask and later components choosing between them.

Model choice belongs here, not in Phase 1. A vLLM process loads a single model, and the endpoint's model list returns exactly one entry — so a model picker against today's deployment is a control with nothing to pick, where any value but the loaded one is a 404. Model choice becomes meaningful the moment a second endpoint exists, which is the same moment the roster does. If an endpoint later serves several models, the list is read from the server rather than typed by hand.

Honest position: the problem in front of us does not require it. One endpoint plus the reasoning knob solves the ask. A roster earns its keep when we actually have several endpoints to switch between, and it is a real migration of the settings schema from flat fields to a list.

Recommendation: ship Phase 1, run the experiments it enables, and build the roster when a second endpoint exists. Nothing in Phase 1 blocks it — adding a model field beside the reasoning field is the same code path.

Deliberately not doing

  • No change to the shared provider interface.
  • No reasoning control for the local Ollama provider — different API, different knob.
  • No change to the existing reasoning-stripping code; it stays harmless with thinking off.
  • No model picker. One vLLM process serves one model, so there is nothing to choose until a second endpoint exists. Model choice is deferred, not withheld.
  • No new settings mechanism — Phase 2 extends the one we have.

Open questions

  1. Which vLLM version is deployed? It decides the request field — though the Phase 1 probe answers it either way.
  2. What does the Ask control default to? The serving default stays reasoning-on, so "no override" means everyone keeps paying ~15 seconds. Either inherit the server default and stay slow-by-default, or default the Ask lane to no reasoning and let people opt in. This is the latency decision now.
  3. Phase 2 roster: build it now, or when a second endpoint actually exists?
  4. Ask gains request fields rather than new routes — confirm the team-mode gated path still passes before Phase 1 is called shipped.
